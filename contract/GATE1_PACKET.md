# Gate 1 Packet: Independent Contract Verification

**Instructions for Predictors (Two Independent Evaluators):**
1. Read `contract/SPEC.md` carefully.
2. Without consulting the test harness code or each other, predict the return status (`applied`, `duplicate`, or `rejected`) and cited rule (`R0`–`R10`) for each step in the 10 scenarios below.
3. Also predict the final database state (`payments` row and `ledger` entries).
4. Fill in the Answer Sheet at the bottom.
5. After both evaluators have completed their predictions, compare against `contract/GATE1_KEY.md`.
6. Any disagreement between either evaluator and the key indicates an ambiguity in `SPEC.md` that must be clarified before freezing.

---

## Scenario 1: Case 002 (Duplicate Delivery)
- **Step 1:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500 (50,000 paise). Canonical JSON, valid signature.
- **Step 2:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500 (50,000 paise). Identical payload and signature.

## Scenario 2: Case 004 (Second Capture on Same Payment)
- **Step 1:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500 (50,000 paise). Valid signature.
- **Step 2:** Event `evt_002`, `payment.captured`, `pay_1`, amount ₹300 (30,000 paise). Distinct event ID, same payment ID, valid signature.

## Scenario 3: Case 007 (Exact Boundary Refunds)
- **Step 1:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500 (50,000 paise). Valid signature.
- **Step 2:** Event `evt_r1`, `refund.processed`, `pay_1`, `rfd_1`, amount ₹200 (20,000 paise). Valid signature.
- **Step 3:** Event `evt_r2`, `refund.processed`, `pay_1`, `rfd_2`, amount ₹300 (30,000 paise). Valid signature.

## Scenario 4: Case 009 (Accumulated Refund Over-Bound)
- **Step 1:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500 (50,000 paise). Valid signature.
- **Step 2:** Event `evt_r1`, `refund.processed`, `pay_1`, `rfd_1`, amount ₹200 (20,000 paise). Valid signature.
- **Step 3:** Event `evt_rover2`, `refund.processed`, `pay_1`, `rfd_over2`, amount ₹350 (35,000 paise). Valid signature.

## Scenario 5: Case 010 (Refund Arriving Before Capture)
- **Step 1:** Event `evt_r1`, `refund.processed`, `pay_1`, `rfd_1`, amount ₹200 (20,000 paise). Valid signature. No prior capture exists.

## Scenario 6: Case 016 (Boolean Amount)
- **Step 1:** Event `evt_bool`, `payment.captured`, `pay_1`, amount `true` (JSON boolean literal). Valid signature over raw body bytes.

## Scenario 7: Case 039 (Uppercase Hex Signature)
- **Step 1:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500 (50,000 paise). Signature is valid hex HMAC but formatted in UPPERCASE.

## Scenario 8: Case 041 (Signature Over Re-Serialized JSON)
- **Step 1:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500. Raw body contains whitespace spaces `", "`. Signature was generated by parsing JSON and calling `json.dumps(parsed)` with default compact/different whitespace.

## Scenario 9: Case 047 (Rejection Followed by Valid Redelivery)
- **Step 1:** Event `evt_r1`, `refund.processed`, `pay_1`, `rfd_1`, amount ₹200. No prior capture exists.
- **Step 2:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500. Valid signature.
- **Step 3:** Event `evt_r1`, `refund.processed`, `pay_1`, `rfd_1`, amount ₹200. Exactly redelivered with valid signature.

## Scenario 10: Case 049 (Applied Event Redelivered with Bad Signature)
- **Step 1:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500. Valid signature.
- **Step 2:** Event `evt_001`, `payment.captured`, `pay_1`, amount ₹500. Identical payload, but signature has a flipped/corrupted byte.
